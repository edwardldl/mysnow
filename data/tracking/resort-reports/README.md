# Resort-reported snowfall — live monitoring & forecast verification

Resorts publish their own snow reports each morning ("new snow in the
last 24 hours"). This directory holds the collected reports and their
comparison against MySnow's model forecasts, so forecast skill can be
checked against what resorts actually reported, as it happens.

## Source

**SnoCountry JSON API** (`feeds.snocountry.net/getSnowReport.php`) —
chosen 2026-11-16 after a live survey of SnoCountry, OnTheSnow,
OpenSnow, and resorts' own snow-report pages:

* Structured JSON with documented fields: `newSnowMin`/`newSnowMax`
  (new snow, last 24 h, inches), `snowLast48Hours`, `avgBaseDepthMin`/
  `avgBaseDepthMax`, `reportDateTime`, operating status.
* Coverage: all **129** catalogue resorts have a SnoCountry id
  (`snocountry_ids.json`; 127 matched by name+state against
  `getResortList`, 2 hand-verified — Devil's Head is filed as "Devils
  Head Resort", Mt Rose as "Mt Rose Ski Tahoe" under CA). The map was
  generated from the API's resort list on 2026-11-16; regenerate it the
  same way if the catalogue changes.
* OnTheSnow and OpenSnow offer no public structured feed (JS apps;
  OpenSnow's data is subscription-gated; the weather.com ski API that
  republishes OnTheSnow data needs a restricted key). Resort pages are
  heterogeneous JS apps — one bespoke parser per resort is not
  maintainable as a primary source.

**Access note:** production SnoCountry keys are purchased. The
collector defaults to SnoCountry's publicly documented sample key
(`SnoCountry.example`), which SnoCountry provides for development /
evaluation; it caps multi-resort responses at 3 resorts, so the
collector uses the documented single-resort request form (SnoCountry's
guidelines place no limit on single ski area requests) at a polite
rate. **A standing production monitor should use a purchased key.**

## Layout

* `snocountry_ids.json` — catalogue slug → SnoCountry id/name/state.
* `raw/<collection UTC date>/<slug>.json` — raw API responses, kept
  verbatim so parsing can be redone.
* `reports-<collection UTC date>.jsonl` — parsed records (snow values
  in cm, raw inches retained; see `slr_calibration/resort_reports.py`).
* `comparisons.jsonl` — derived comparison rows, regenerated by
  `scripts/report_resort_verification.py` on every run.
* `verification-<date>.md` — human-readable comparison reports.

## Alignment (summary)

A report dated local date `D` (report timestamp interpreted in the
resort's registry timezone) is matched to the model window ending
07:00 local on `D`, and compared against the last forecast issued
before that window began. The full rule and its caveats (afternoon
reports, "since lifts closed" reporters, min/max range vs the model's
three points) are documented in
`training/slr_calibration/src/slr_calibration/resort_reports.py`.
